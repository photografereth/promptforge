# Pilar 5 (parte 3): Logging Centralizado — Design

Status: Approved
Date: 2026-09-23
Depends on: Pilar 1 (auth/dados)
Unblocks: nada diretamente — reduz o tempo pra diagnosticar um problema em produção depois que o log nativo da Vercel expira

## Contexto

Último dos três subsistemas independentes do Pilar 5 (Termos/Privacidade
e rate limit por IP já entregues em specs anteriores).

Levantamento feito no código antes de escrever este spec:

- **17 chamadas de `console.log/warn/error`** espalhadas em 9 arquivos
  (`api/enhance.ts`, `api/autofill.ts`, `api/analyze-references.ts`,
  `api/parse-product-url.ts`, `api/_lib/gemini.ts`,
  `api/_lib/rateLimit/decideIpRateLimit.ts`, `api/cron/billing.ts`,
  `api/billing/[action].ts`, `api/webhooks/mercadopago.ts`), sem
  estrutura (string solta + argumento livre), sem nível consistente além
  do método usado (`log`/`warn`/`error`), sem jeito de filtrar por campo
  no painel da Vercel.
- Já existe uma disciplina de **não vazar dados pessoais** em alguns
  lugares — `billing/[action].ts:24`, `cron/billing.ts:25` e
  `webhooks/mercadopago.ts:66` já logam só `error.name` ("a mensagem
  pode conter dados pessoais", comentário existente no código) — mas
  **não é seguida em todo lugar**: `enhance.ts:68`, `autofill.ts:201`,
  `analyze-references.ts:167`, `parse-product-url.ts:212` e `:74` logam
  `error.message` direto, que pode conter conteúdo enviado pelo usuário
  ou detalhe interno do provedor (Gemini).
- **Retenção de log nativo da Vercel no plano Hobby é curta**, sem log
  drain persistente. O próprio Pilar 2 já sofreu com isso na prática — a
  depuração do webhook do Mercado Pago (registrada em
  `docs/superpowers/plans/2026-09-18-mercadopago-billing.md`/histórico
  de commits) levou horas por falta de rastro histórico.

## Objetivo

Um logger compartilhado com formato estruturado (JSON, nível
consistente) que **substitui** as 17 chamadas atuais de `console.*`,
corrigindo o vazamento de `error.message` onde existe hoje. Eventos de
nível `error` também são persistidos no Supabase, sobrevivendo à
retenção curta da Vercel.

## Não-objetivos (fora de escopo desta parte do Pilar 5)

- Integração com serviço externo de log (Axiom, BetterStack, Sentry,
  etc.) — decisão tomada no brainstorming: fica fora do padrão
  Vercel+Supabase que o projeto vem seguindo, e exigiria o usuário criar
  conta num serviço novo.
- Correlação entre múltiplas linhas de log da mesma requisição (request
  ID / trace ID) — o tráfego atual é baixo o suficiente pra não precisar
  disso ainda; a maioria dos eventos hoje já é uma linha só por
  falha. Revisitar se isso virar uma dor real.
- Persistir eventos de nível `info`/`warn` no Supabase — só `error`
  persiste; `info`/`warn` continuam só no console estruturado. A
  maioria das ocorrências de `warn` hoje são fallbacks que já
  recuperaram sozinhos (ex.: Gemini falhou, respondeu com heurística
  local) — não valem o custo de escrita nem a latência extra numa
  resposta que já está no caminho de recuperação de erro.
- Dashboards, alertas ou qualquer visualização sobre os logs
  persistidos — só a tabela existe; consultá-la é manual via SQL
  Editor do Supabase por enquanto.

## Design

### Modelo de dados (Supabase Postgres, migração `0005_system_logs.sql`)

```sql
create table public.system_logs (
  id bigint generated by default as identity primary key,
  level text not null,
  event text not null,
  details jsonb,
  created_at timestamptz not null default now()
);

alter table public.system_logs enable row level security;
-- Sem policies: só o service role acessa (mesmo padrão de gemini_circuit_breaker e ip_rate_limit).
```

Sem função RPC aqui — ao contrário das cotas/rate-limit, não há
incremento atômico envolvido, só um `insert` simples; não há o mesmo
risco de privilégio default do Supabase porque não estamos criando uma
função `security definer` nova (o insert acontece via `supabaseAdmin`,
que já usa a service role key diretamente, sem RPC).

Limpeza: linhas com mais de 30 dias são apagadas pelo cron diário já
existente (`api/cron/billing.ts`), mesmo padrão do Pilar 5 parte 2
(`cleanupOldWindows`) — sem cron novo.

### Logger — `api/_lib/logging/logger.ts`

```ts
export function logInfo(event: string, details?: Record<string, unknown>): void;
export function logWarn(event: string, details?: Record<string, unknown>): void;
export function logError(event: string, details?: Record<string, unknown>): Promise<void>;
```

`logInfo`/`logWarn` só escrevem uma linha JSON estruturada no console
(`{ level, event, ...details }`) via `console.log`/`console.warn` — sem
I/O, síncronas. `logError` faz o mesmo via `console.error` **e** persiste
a linha em `system_logs`, com `await` (lição da revisão do Pilar 3: uma
escrita "fire-and-forget" pode ser descartada pela Vercel antes de
completar) — envolta no próprio try/catch, uma falha ao persistir nunca
deve derrubar o handler que estava logando o erro original.

### Extração segura do nome do erro — `api/_lib/logging/errorName.ts`

```ts
export function errorName(err: unknown): string;
```

Extrai só `err.name` (ex.: `"TypeError"`, `"MercadoPagoError"`) — nunca
`err.message`. Substitui o padrão já repetido 3x no código
(`error instanceof Error ? error.name : 'unknown'`) por uma função só,
e vira a forma padrão de logar qualquer erro capturado daqui pra frente:
`logError('evento', { errorName: errorName(err) })`, nunca
`logError('evento', { message: err.message })`.

### Migração dos 17 pontos de log existentes

Cada `console.log/warn/error` atual vira uma chamada ao logger, mapeado
por severidade real (não pelo método de console usado hoje, que nem
sempre reflete a severidade):

| Nível | Arquivos/eventos |
|---|---|
| `error` | `CRON_SECRET`/`MP_WEBHOOK_SECRET` ausente, catch de topo de `cron/billing.ts`/`billing/[action].ts`/`webhooks/mercadopago.ts`, falha do rate limit por IP (`decideIpRateLimit.ts`) |
| `warn` | Fallback do Gemini nas 4 rotas de IA (`error.message` **removido**, só `errorName`), falha ao ler/escrever o circuit breaker (`gemini.ts`), falha ao limpar `ip_rate_limit` no cron, falha do fetch de diagnóstico de `payment` no webhook |
| `info` | Webhook recebido (`type`, `dataId` — já são campos seguros), nota de busca de metadados de URL (`err.message` **removido**) |

## Testes

Mesmo padrão TDD dos pilares anteriores:

- `errorName`: pure function — `Error` real devolve `.name`, valor não-Error devolve `'unknown'`.
- `logError`: repo em memória (mesmo padrão de `UsageRepo`/`IpRateLimitRepo`) —
  confirma que a persistência é chamada com os campos certos, e que uma
  falha no repo não propaga (o handler chamador nunca quebra por causa
  do logger).
- `logInfo`/`logWarn`: não têm I/O — verificados só manualmente (mesmo
  padrão de rotas não testadas diretamente neste projeto), já que são
  só uma chamada de `console.*`.

## Riscos e mitigação

| Risco | Mitigação |
|---|---|
| `error.message` continuar vazando em algum lugar não migrado | Os 17 pontos atuais estão listados explicitamente no plano; a revisão final confere que nenhuma chamada de `console.*` sobrou fora do logger nas áreas tocadas. |
| Tabela `system_logs` crescendo sem controle sob uma falha recorrente | Só `error` persiste (não todo log), e o cron diário já existente limpa linhas com mais de 30 dias. |
| `await logError(...)` adicionar latência perceptível numa resposta de erro ao usuário | Só os catches de erro real (já são o caminho lento/exceção) usam `logError`; os fallbacks de recuperação rápida (Gemini, circuit breaker) usam `logWarn`, síncrono, sem I/O. |
