# Pilar 5 (parte 3): Logging Centralizado — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Substituir as 17 chamadas atuais de `console.*` por um logger estruturado, corrigindo o vazamento de `error.message` em 5 delas, com eventos `error` persistidos no Supabase.

**Architecture:** Módulo novo `api/_lib/logging/` — `errorName` (pure), `logInfo`/`logWarn` (console estruturado, sem I/O) e `logError` (console + persistência injetável, mesmo padrão de DI de `api/_lib/quota/` e `api/_lib/rateLimit/`). `requireIpRateLimit` ganha um parâmetro extra pra logar seu próprio caminho de erro sem introduzir uma chamada de rede real durante os testes existentes. Os 8 arquivos de rota/serviço trocam `console.*` pelo logger.

**Tech Stack:** TypeScript, Vitest, Supabase Postgres (insert simples, sem RPC — ver spec).

**Spec:** `docs/superpowers/specs/2026-09-23-centralized-logging-design.md`

## Global Constraints

- `logInfo`/`logWarn` nunca fazem I/O — só uma linha JSON no console. `logError` faz console **e** persiste, com `await` (lição do Pilar 3: fire-and-forget pode ser descartado pela Vercel).
- Nunca logar `error.message` ou conteúdo enviado pelo usuário — só `errorName(err)` (extrai `.name`) e campos estruturados conhecidos como seguros.
- Qualquer função que já tem teste próprio e passa a chamar `logError` precisa aceitar o repo de log como parâmetro injetável — sem isso, o teste dispararia uma chamada de rede real contra o Supabase de mentira do `vitest.config.ts` (mesma lição do Pilar 3: repo hardcoded não é testável, e aqui o risco extra é a tentativa de rede em teste unitário).
- Import relativo dentro de `api/` sempre com extensão `.js`.

## Review Focus

- **`logError` chamado de dentro de uma função já testada sem o repo injetável**, fazendo um teste unitário tentar uma chamada de rede real contra `https://test.supabase.co` (dummy, do `vitest.config.ts`). Verificado task a task: toda chamada de `logError` dentro de código com teste próprio (só `requireIpRateLimit.ts` se aplica — os outros 8 arquivos que chamam o logger não têm teste) usa um repo injetado explicitamente no teste, nunca o default.
- **`error.message` sobrevivendo em algum dos 17 pontos migrados.** A Task 5 lista os 8 arquivos e 16 pontos restantes (o 17º já foi tratado nas Tasks 3/4) explicitamente; a revisão final confere que nenhum `console.*` direto sobrou nesses arquivos.
- **Nível de severidade trocado** (ex.: um fallback que já recuperou virar `error` e persistir sem necessidade, ou uma falha real de configuração virar só `warn` e nunca aparecer no Supabase). A tabela da spec ("Migração dos 17 pontos") é a fonte da verdade; a Task 5 segue ela item a item.
- **Falha ao persistir um log derrubando o handler que estava logando o erro original.** `logError` sempre envolve a chamada de persistência no próprio try/catch — testado na Task 3.
- **Tabela `system_logs` sem limpeza**, crescendo indefinidamente. A Task 6 acrescenta a limpeza de 30 dias no cron diário já existente, mesmo padrão do `cleanupOldWindows` do Pilar 5 parte 2.

export async function logError(
  event: string,
  details?: Record<string, unknown>,
  repo: LogRepo = createSupabaseRepo()

}

- [ ] **Step 5: Implementar o ajuste em `api/_lib/rateLimit/requireIpRateLimit.ts`**

```ts
import type { VercelRequest, VercelResponse } from '@vercel/node';
import { decideIpRateLimit } from './decideIpRateLimit.js';
import { createSupabaseRepo } from './repo.js';
import { getClientIp } from './getClientIp.js';
import type { IpRateLimitRepo } from './types.js';
import { logError } from '../logging/logger.js';
import { createSupabaseRepo as createSupabaseLogRepo } from '../logging/repo.js';
import type { LogRepo } from '../logging/types.js';

// Chamar como a PRIMEIRA linha do handler, antes de `authenticate`:
// `if (!(await requireIpRateLimit(req, res))) return;`
export async function requireIpRateLimit(
  req: VercelRequest,
  res: VercelResponse,
  repo: IpRateLimitRepo = createSupabaseRepo(),
  now: Date = new Date(),
  logRepo: LogRepo = createSupabaseLogRepo()
): Promise<boolean> {
  const ip = getClientIp(req);
  const decision = await decideIpRateLimit(repo, ip, now);
  if (decision === 'ok') return true;
  if (decision === 'limited') {
    res.status(429).json({
      error: 'Muitas requisições. Tente novamente em alguns minutos.',
      code: 'rate_limited',
    });
  } else {
    await logError('ip_rate_limit_check_failed', { ip }, logRepo);
    res.status(503).json({ error: 'Não foi possível processar a requisição. Tente novamente.' });
  }
  return false;
}
```
